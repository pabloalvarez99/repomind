# Case study: RepoMind v0.3.0

**In one line:** a repository Q&A service that answers with `path:start-end` citations or
refuses outright, runs end to end with no API key and no network call, and is gated by two
committed eval suites that report `judge: null` and `billed_usd: 0.0`.

**Read time: two minutes. Setup required: none.** Four decisions are described below, each
with the trade-off it bought. The last section states plainly what the eval scores do *not*
prove, because a portfolio project that only advertises its wins is not evidence.

## Problem

Code assistants routinely make two trust-eroding moves: they accept an overly broad filesystem
target, and they answer without a precise source location. RepoMind explores a narrower
question. Can a service locate useful Python definitions, cite exact lines, and refuse when it
has no evidence — fully offline, and for $0?

## Decision 1 — AST chunks, not embeddings, for v0.1.0

Embeddings are the reflexive choice for code retrieval. For this milestone they are the wrong
first move, for three reasons.

- **Line evidence is the product.** Fixed-size text windows straddle definition boundaries, so
  the cited range is an artifact of the chunker rather than a fact about the code. Python's AST
  already reports `lineno`/`end_lineno` for each definition. A citation derived from the AST is
  correct by construction; a citation derived from a 512-token window is approximately correct.
- **The free path must survive with no credentials.** An embedding model means either a billed
  provider or a downloaded model with its own footprint. Both break the promise that a reviewer
  can clone, install, and run without an account.
- **Failure has to be inspectable.** `chunk_id = path::qualname` is a contract a reviewer can
  verify by eye. Vector-space neighborhoods are not.

**What it costs:** no synonym or paraphrase matching. Asking for "the thing that merges ranked
lists" works only because the docstring and identifier share tokens with the question, not
because the system understands the concept. Semantic retrieval is the natural next milestone,
and it should be added *on top of* a citation layer that is already trustworthy — not
underneath one that is not.

## Decision 2 — `repo_id` against a closed catalog, not caller-supplied paths

The obvious API is `{"path": "/some/repo"}`. RepoMind refuses to offer it. Requests name a
repository id (`mini`, `production_rag`, `mini_js`); the server maps ids to roots in
[`src/repomind/catalog.py`](../src/repomind/catalog.py). A request value is never joined onto a
filesystem path, so there is no path-traversal surface to sanitize and no sanitizer to get
wrong.

One validity function — `validate_repo_id` — backs every surface. The allowlist is *derived*
from `catalog_roots()`, so an id the catalog publishes cannot 422 on POST while GET accepts
it. That exact bug existed for `production_rag` (underscore rejected by a slug regex); v0.2.0
closes it. A blank id is 422, a path-shaped id is 400, a well-formed stranger is 404.

The catalog is closed in both directions. The environment may repoint the root behind an
already-known id (`REPOMIND_CATALOG_PRODUCTION_RAG`), but it cannot add an id, and evaluation
callers disable the override entirely so CI always measures committed bytes. Beyond that, the
walker reads source as text, skips symlinks and ignored or cached paths, and never imports the
target — it will not execute fixture code to answer a question about it.

**What it costs and what it is not:** you cannot point the hosted free path at an arbitrary
local repository through the HTTP API, which is a real product limitation. And this is not a
complete hostile repository sandbox — it removes code execution and caller-selected traversal
from the free path, which is a smaller claim than "safe against a malicious repository". See
[ADR 0001](adr/0001-closed-catalog-parse-only.md) and
[ADR 0003](adr/0003-content-addressed-catalog-index.md).

## Decision 3 — a committed snapshot, not a sibling checkout in CI

Dogfooding RepoMind on a real project needs that project present at eval time. Cloning a
sibling repository in CI was rejected: the eval would then depend on network availability, on
another repository's default branch, and on whichever commit happened to be current — a green
run would stop being reproducible, and a red run would stop being informative.

Instead, `fixtures/production_rag/` holds a small frozen selection from the sibling project at
approximately `d882c9a`: the query pipeline, graph builder, RRF implementation, fake embedding
provider, guardrail, and API route. Those bytes are committed, versioned, and attributed in
[`fixtures/production_rag/NOTICE.md`](../fixtures/production_rag/NOTICE.md). The eval measures
exactly what a reviewer can read.

**What it costs:** the snapshot drifts from its upstream, and refreshing it is a manual step. A
citation into the snapshot is evidence about the snapshot, not a live claim about the sibling
repository's current state. That trade — reproducibility over freshness — is the right one for
a gate whose job is catching regressions in *this* repository.

## Decision 4 — content-addressed index, one more language, optional history

v0.2.0 gives every chunk a content hash and every repository a tree hash, so re-ingesting an
unchanged fixture is a measured no-op and `GET /v1/catalog` can publish what this instance
actually serves. Python still uses the stdlib AST. JavaScript/TypeScript is free-path plumbing
on a tiny committed fixture (`mini_js`): `Where is foo defined?` → `src/foo.js` with a
path:line citation. That is multi-language wiring, not SOTA. Optional tree-sitter stays behind
an extra so default CI never needs network for a grammar.

## Decision 5 — committed history snapshots beat git(1) on serverless (v0.3.0)

v0.2.0 advertised `GET /v1/code/history` via local git. On Vercel that surface always returned
`503 capability_missing`: no git binary, and fixtures are not stand-alone work trees.
Documenting the 503 is not a product. v0.3.0 commits deterministic
`.repomind/history.jsonl` tables per fixture and reads those on the request path
([ADR 0004](adr/0004-committed-history-snapshots.md)). A hiring manager gets `200` with path
history that is an honest snapshot claim — not live GitHub, and not a silent empty list.

## Decision 6 — dogfood a pinned P1 snapshot; who-calls stays AST-honest

`production_rag` is refreshed from a pinned SHA of `pabloalvarez99/production-rag` `src/`
only. The pin is catalog metadata (`source_sha`), never a live clone. Incoming refs
(`GET /v1/code/refs`) walk Python AST call sites: a known function can have callers, and a
leaf may honestly return zero. No invented edges.

## Decision 7 — what 14/14 and 8/8 actually prove

Both suites pass on committed bytes. Both scorecards report `provider:
deterministic-lexical`, `judge: null`, and `billed_usd: 0.0`. That last line is the point: no
model scored these runs, so there is no grader to flatter the system.

**They do prove:**

- Exact-symbol requests return the exact definition, and each citation's `path`,
  `start_line`, and `end_line` match the AST range of that definition.
- Weak evidence produces the fixed refusal with an empty citation list, rather than a
  plausible-sounding answer. Refusal is covered in both suites.
- Definitions inside gitignored files are still reachable, and hierarchical `.gitignore`
  handling behaves as documented.
- CLI, HTTP API, symbol outline, and console all sit on one service implementation, so the four
  surfaces cannot disagree.
- The scores are reproducible: same bytes in, same scores out, offline, on a clean CI runner
  with empty provider keys.

**They do not prove:**

- Anything about retrieval quality on arbitrary repositories. Twenty-two questions over two
  small committed corpora is a regression gate, not a benchmark.
- Semantic understanding. Prose questions succeed on lexical overlap with identifiers and
  docstrings; rephrase one far enough and it refuses.
- Deep multi-language analysis. Free-path JS is top-level plumbing on a tiny fixture; incoming
  refs are Python-AST-only.
- Answer *synthesis* quality. Answers are templated statements about located definitions.
  There is no generation step to evaluate, which is why `judge` is `null` rather than a score.
- Scaling behavior. The index is in-memory and rebuilt per process.

A perfect score here means the system is stable and honest on the bytes it ships with. It
deliberately does not mean the system is good at code RAG in general.

## Result

v0.1.0 ships one implementation behind four surfaces: a JSON CLI, `POST /v1/code/ask`,
`GET /v1/code/symbols`, and an accessible local console. CI installs from scratch on Python
3.12 with empty provider keys and runs lint, strict mypy, tests, both eval suites, the CLI, and
live HTTP and UI probes. No credential is required, committed, or read.

The most useful thing in the repository is not the pass rate. It is that the refusal path is
tested, screenshotted, and documented alongside the successes.
